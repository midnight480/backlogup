# BacklogUp

[English](README.md) | [日本語](README_ja.md)

> Fork 元: [common-creation/backlogup](https://github.com/common-creation/backlogup)

## これはなに

Backlog API を叩いて、指定したプロジェクトのデータをバックアップします。  
バックアップしたデータは簡易ビューアで閲覧できるほか、別の Backlog スペース／プロジェクトに移行・移植できます。

## 公式移行ツールとの違い

ヌーラボ公式の移行ツール（[BacklogMigration-Backlog](https://github.com/nulab/BacklogMigration-Backlog)）で移行できずにここへ辿り着いた方向けに、いちばん大きな違いを先に書いておきます。

公式ツールはプロジェクトの**過去履歴をすべて再現**します。過去に存在したすべての状態（ステータス）の定義や、その名称変更の履歴まで含めて反映するため、長く運用してきたプロジェクトほど次の制限に引っかかります。

- 「状態を追加」「状態名の変更」を **9 回以上おこなったプロジェクトは移行できない**
- 一度でも状態を追加したプロジェクトは **ASP からエンタープライズへ移行できない**

BacklogUp は逆のアプローチを取ります。プロジェクトの**最新の断面（スナップショット）だけ**を読み取り、それを移行先に再構築します。プロジェクトの設定変更履歴は一切参照しないため、上記2つの制限はそもそも発生しません。状態変更を30回繰り返してきたプロジェクトでも、新規プロジェクトと同じように移行できます。

| | 公式移行ツール | BacklogUp |
|---|---|---|
| 移行する単位 | プロジェクトの全履歴 | 最新の断面 |
| 状態の追加・改名が9回以上 | ❌ 移行不可 | ✅ 制限なし |
| 状態追加済みプロジェクトの ASP→エンタープライズ | ❌ 移行不可 | ✅ 制限なし |
| カスタム状態 | 再現される | 再現されない（標準4状態のみ） |
| 元の作成者・作成日時 | ネイティブな項目として反映 | 本文・コメント冒頭にテキストの注記として付与 |
| 移行前のオフライン閲覧 | — | ローカルビューアを同梱 |

### トレードオフ

履歴を捨てることで互換性を得ているので、当然その代償があります。

- **カスタム状態は再現されません。** 適用されるのは標準の4状態（未対応／処理中／処理済み／完了）のみです。カスタム状態のまま止まっている課題は、移行先では状態が変更されずに登録されます。
- **履歴は「本文」として再現され、ネイティブな変更履歴にはなりません。** コメントは古い順に再投稿されますが、元の作成者と日時はテキストの注記として本文に入ります。移行先の変更履歴上は、実行に使った API ユーザーと移行日時が記録されます。
- **属性の定義は「再作成」であって「保存」ではありません。** 移行先に存在しない種別・カテゴリー・マイルストーンは自動作成されますが、元と同一のオブジェクトではありません。

プロジェクトの全履歴を忠実に再現する必要がある場合は公式ツールを使ってください。公式ツールが自分のプロジェクトでは動かない場合、あるいは中身を移して閲覧できれば十分な場合は、こちらが現実的な代替になります。

## 主な機能・仕様 (Features & Specifications)

### 1. データバックアップ機能 (`npm run backup`)
- **完全ローカル保存**: 指定した Backlog プロジェクトのデータをローカル環境に JSON および実ファイルとして保存します。
- **バックアップ対象**:
  - **課題 (Issues)**: 課題本体、ステータス、優先度、カスタム属性、コメント、添付ファイル
  - **Wiki**: Wiki ページ本文、スター、添付ファイル、タグ
  - **ドキュメント (Documents)**: フォルダ/ファイルのツリー構造、ドキュメント本体、コメント（リプライ含む）、添付ファイル
  - **共有ファイル (Shared Files)**: ファイル共有領域をフォルダ階層ごと再帰的に走査し、ファイル一覧 (`shared-files/list.json`) を作成。実ファイルのダウンロードは件数が多くなりがちなため、`npm run backup` では行わず、別コマンド `npm run download:sharedfiles` で個別／一括に、中断後の再開もできる形で取得します（[詳細](#共有ファイルのダウンロード)）。元のフォルダ構造・ファイル名のままローカルに保存されます。
  - **プロジェクト設定**: 課題種別、カテゴリ、マイルストーン、メンバー一覧、**ライセンス情報**（プラン種別、ユーザー上限、ストレージ容量など）
  - **ユーザー情報**: ユーザーメタデータ、アイコン画像
- **差分更新対応**: 既に取得済みのデータが存在する場合、更新分のみを差分取得し、2回目以降のバックアップを高速化します。

### 2. ローカルアーカイブ・ビューア (SPA)
バックアップしたデータをオフラインで高速かつ直感的に閲覧できる React + Vite ベースのビューアです。

- **モダンなUIレイアウト**:
  - ヘッダーナビゲーションによる画面の広さを活かしたレイアウト構成（サイドバーレス）。
  - Tailwind CSS を活用したセマンティックなテーマカラー（緑色ベースの Primary カラー）と一貫したデザインシステム。
- **ダッシュボード**:
  - プロジェクトの基本情報、バックアップ進捗/統計、ライセンス情報などを一覧表示。
- **課題エクスプローラー**:
  - ページネーション対応の一覧テーブル表示（ステータスや優先度をバッジで視覚化）。
  - インデックスベースのローカルキーワード検索による課題の高速絞り込み。
- **Wiki / ドキュメント ビューア**:
  - 左ペインにパス構造から自動生成したフォルダツリーを表示。
  - **インクリメンタル検索窓**を搭載し、入力した文字列でページ名・ファイル名からリアルタイムにツリーをフィルタリング可能。
  - Wiki は Markdown 形式でのレンダリング、ドキュメントは Tiptap (ProseMirror) によるリッチテキスト表示をサポート。
  - 添付ファイルのダウンロード、コメントスレッドの階層表示にも対応。
- **ユーザー設定 (Settings モーダル)**:
  - **多言語対応 (i18n)**: 日本語 (JA) / 英語 (EN) の即時切り替え。
  - **テーマ設定**: ライトモード / ダークモードのトグル切り替え。
  - 各設定値はブラウザの `localStorage` に保存され、リロード後も維持されます。

### 3. データ移行機能 (`npm run migrate`)
バックアップしたデータ（課題、Wiki、添付ファイル、各種設定）を別の Backlog スペース／プロジェクトに移植・移行する機能です。

- **ユーザー自動マッピング**: 移行元のユーザー一覧と移行先のユーザーをメールアドレス完全一致および名前で自動紐付け。手動 `user-mapping.json` にも対応。
- **設定・属性の自動同調**: 種別・カテゴリー・バージョンを移行先から抽出・同調（不足分は自動作成）。
- **課題・Wiki・添付ファイルの連続再現**: 古い順に課題・コメント・添付ファイルを投稿。本文・コメントの先頭に元作成者／作成日／元課題キーのメタデータ注記を付与。
- **対象範囲**: 移行されるのは課題と Wiki のみです。ドキュメントと共有ファイルはバックアップはされますが**移行されません**（[移行の制限事項](#移行の制限事項)を参照）。

## かんたん起動（非エンジニア向け・ほぼワンクリック）

コマンド操作に不慣れな方（事業部の情シス担当の方など）向けに、**ファイルをダブルクリックするだけ**で使える起動方法を用意しています。日本語のメニューが表示されるので、番号を選ぶだけでバックアップ・共有ファイルのダウンロード・ビューア起動ができます。

| OS | ダブルクリックするファイル |
|----|--------------------------|
| Windows | `start-windows.bat` |
| macOS | `start-mac.command` |

**使い方（共通）**

1. このリポジトリを ZIP でダウンロードして展開（または `git clone`）します。
2. お使いの OS に合わせて、上記のファイルをダブルクリックします。
   - 初回は Node.js のインストール確認と、必要パッケージの自動セットアップ（数分）が走ります。
   - Node.js が入っていない場合は案内に従って [公式サイト](https://nodejs.org/ja/download)から LTS 版を入れてください。
3. 初回は設定ファイル `.env` が自動で作られ、メモ帳／テキストエディットが開きます。
   次の3つを入力して保存してください（取得方法は下の表のとおり）。

   | 項目 | 入れる値 |
   |------|---------|
   | `BACKLOG_HOST` | Backlog のドメイン（例: `xxx.backlog.com`） |
   | `BACKLOG_API_KEY` | API キー（Backlog の 個人設定 → API から取得） |
   | `BACKLOG_PROJECT_KEY` | プロジェクトキー |

4. メニューが出たら、やりたいことの番号を入力して Enter:

   ```
   1) バックアップを実行する
   2) 共有ファイルをすべてダウンロードする
   3) ビューア（閲覧画面）を起動する
   4) データを全消去してからバックアップし直す
   5) 設定ファイル(.env)を開いて編集する
   0) 終了する
   ```

> 💡 macOS で初回に「開発元を確認できないため開けません」と出る場合は、`start-mac.command` を**右クリック → 開く**を選ぶと実行できます。

## バックアップの取り方

1. `sample.env` を `.env` にコピー
2. `.env` のコメント通りに必要事項を入力する
   - `BACKLOG_HOST` — Backlog のドメイン（例: `xxx.backlog.com`）
   - `BACKLOG_API_KEY` — API キー（個人設定 → API から取得）
   - `BACKLOG_PROJECT_KEY` — プロジェクトキー
3. `npm run backup` でバックアップを開始する

※ Backlog プロジェクトの規模によっては、バックアップに時間がかかります。

### ⚠️ プロジェクトキーを変更する場合（必須）

抽出されるデータはプロジェクトキーごとにフォルダが分かれておらず、常に同じ `dist/assets` ディレクトリに保存されます。
そのため、`.env` で **異なるプロジェクトキーに変更してバックアップを取得する際は、必ず事前にデータをリセットして総入れ替え** する必要があります。
（これを怠ると、複数のプロジェクトのデータが混ざってしまい、ビューアの表示が崩れる原因となります）

既存のバックアップデータを完全に削除し、新規バックアップを開始するには、`CLEAN_BACKUP=true` を付与して実行してください。

```bash
CLEAN_BACKUP=true npm run backup
```

## データ移行のやり方 (`npm run migrate`)

バックアップ済みのデータを、別の Backlog スペースまたは別プロジェクトへ移行します。

### 事前準備・手順

1. 事前に `npm run backup` を実行し、ローカルに最新データを取得しておきます。
2. `.env` に移行先 (Target Space) の設定を追加します：

```env
# 移行先のBacklogドメイン
TARGET_BACKLOG_HOST=target.backlog.com

# 移行先のBacklog APIキー
TARGET_BACKLOG_API_KEY=YYYYYYYYYYYYYYYYYYYYYYYYYYY

# 移行先のプロジェクトキー
TARGET_BACKLOG_PROJECT_KEY=TARGET_PROJ

# 移行先プロジェクトにすでに課題が存在する場合でも登録を継続する場合は true に設定（既定値: false）
ALLOW_EXISTING_ISSUES=false
```

3. 移行コマンドを実行します：

```bash
npm run migrate
```

### ユーザーマッピングの手動カスタマイズ (`user-mapping.json`)

基本的にはメールアドレスおよび名前で全自動マッピングが行われますが、手動でユーザーの紐付けを指定したい場合は `dist/assets/user-mapping.json` を作成して指定できます：

```json
{
  "yamada@example.com": "yamada_target@example.com",
  "山田 太郎": "Target Space Yamadaro",
  "1001": 2005
}
```

### 事前検証 (Pre-flight Check) と安全機能
- **API権限確認**: APIキー所有ユーザーが移行先プロジェクトに参加しているかを事前に検証します。
- **同一プロジェクト移行防止**: 移行元と移行先が同一プロジェクトの場合は誤上書きを防ぐため自動的にエラー停止します。
- **既存課題チェック**: 移行先プロジェクトにすでに課題が存在する場合は安全のため一時停止します。課題番号を無視して継続する場合は `.env` に `ALLOW_EXISTING_ISSUES=true` を指定してください。

### 移行の制限事項

以下は公式ツールのドキュメントの転記ではなく、`scripts/migrate/` の実装を読んで洗い出したものです。

**まったく移行されないもの**

1. **ドキュメント** — `npm run backup` ではバックアップされますが、`npm run migrate` が処理するのは課題と Wiki だけです（`scripts/migrate/index.mts`）。
2. **共有ファイル・Git・Subversion。**
3. **カスタム属性（カスタムフィールド）** — 値の読み取り・登録処理自体が存在しません。移行先の課題ではカスタム属性は空になります。
4. **スター** — `stars.json` にバックアップはされますが、移行先には再現されません。
5. **コメントの添付ファイル** — 課題本体の添付ファイルは移行されますが、個々のコメントに添付されたファイルは移行されません（`issue-migrator.mts`）。
6. **Wiki のタグと更新履歴。**
7. **お知らせの既読状態。** なお移行中はメール通知も送信されません（全処理で `mailNotify: false`）。

**再現されるが、変換されるもの**

8. **状態（ステータス）**: 適用されるのは標準4状態（未対応／処理中／処理済み／完了）のみです。変更履歴に記録されたカスタム状態への遷移はスキップされ、最終状態の同調もベストエフォートで、移行先にその状態IDが無ければ失敗は黙って無視されます。
9. **課題キーは維持されません。** 移行先では新しい連番のキーが振られ、元のキーは本文冒頭のメタデータ注記に記録されます。
10. **作成者・日時はテキストになります。** すべての課題とコメントは、移行を実行した API キーの所有者によって、移行実行時の日時で作成されます。元の登録者・登録日・課題キーは `[元課題: ... | 登録者: ... | 登録日: ...]` という形式で本文に付与されます。
11. **種別・カテゴリー・バージョン・マイルストーンは名前で再作成されます**（大文字小文字を無視し、前後の空白を除去して照合）。移行先に無いものは自動作成されるため、過去にだけ存在した種別も作られます。移行後に不要なものは手動で削除してください。種別の作成に失敗した場合、その課題は移行先の先頭の種別に割り当てられます。
12. **照合できなかったユーザーは付け替えられます。** メールアドレス・名前・ユーザーIDのいずれでも一致しない場合、課題は API キー所有者に割り当てられます。制御したい場合は `user-mapping.json` を使ってください。
13. **優先度と完了理由のIDはそのままコピーされます。** 移行先が標準のIDを使っている前提の実装です。
14. **Wiki の添付ファイルは元のファイル名が失われます。** 添付ファイルIDの数値（拡張子なし）のままで保存・再アップロードされます。
15. **親子課題の紐付けは処理順に依存します。** 課題はID昇順で移行され、親は「すでに移行済みの課題」から解決されます。親の移行に失敗した場合、子課題は親なしで登録されます。

**運用上の制約**

16. **同一プロジェクトへの移行はブロックされます** — 移行元と移行先のホストとプロジェクトキーが同じ場合、実行時にエラー停止します。
17. **移行先に既に課題があると中断します。** それでも続行する場合は `.env` に `ALLOW_EXISTING_ISSUES=true` を設定してください。
18. **レート制限**: HTTP 429 を受けると60秒停止して再試行し、5回を超えると中断します。フリープランは制限が厳しいため、規模の大きい移行は現実的ではありません。
19. **同じ移行先スペースに対して複数の移行を並列実行しないでください。** 内蔵の流量制御は単一プロセス前提です。
20. **移行先に同名の Wiki ページがあると上書きされます。** ページ名で照合し、既存ページがあれば複製せずその場で更新します。
21. **Wiki の画像タグを添付ファイルIDで参照している場合**（`#image(123)`）、別スペースへ移行すると画像が表示されません。

## 共有ファイルのダウンロード

共有ファイルは件数が多くなりがちで、Web 画面の一括ダウンロードではタイムアウトすることがあります。本ツールでは「一覧の作成」と「実ファイルのダウンロード」を分離し、API で 1 ファイルずつ確実に取得します（API 実行回数は増えますが、レート制限は自動で 60 秒待機・リトライして回避します）。

1. `npm run backup` を実行すると、共有ファイルの**一覧のみ** `dist/assets/shared-files/list.json` に作成されます（この時点では実ファイルはダウンロードされません）。
2. その後、`npm run download:sharedfiles` で実ファイルを取得します。

```bash
# 一覧を表示する（ID・パス・サイズ）
npm run download:sharedfiles -- --list

# すべてダウンロードする（途中で中断しても、再実行で続きから取得）
npm run download:sharedfiles -- --all

# 指定した ID のファイルだけダウンロードする（個別）
npm run download:sharedfiles -- 123 456
npm run download:sharedfiles -- --id 123,456

# パスに指定文字列を含むファイルをまとめてダウンロードする（例: 特定フォルダ）
npm run download:sharedfiles -- --path 設計書
```

- 既にダウンロード済み（バイト数が一致する）ものは既定でスキップするため、大量のファイルでも安心して中断・再開できます。書き込みは一時ファイル経由でアトミックに行い、中断時に不完全なファイルが残らないようにしています。再取得したい場合は `--force` を付けてください。
- ダウンロードしたファイルは、Backlog 上の**元のフォルダ構造・ファイル名のまま** `dist/assets/shared-files/` 配下に保存されます。
- 1 件でもダウンロードに失敗した場合は終了コードを非 0 にします（自動化が不完全なアーカイブを成功とみなさないため）。

### ビューア画面から選択ダウンロード

`npm run dev` でビューアを起動すると、「共有ファイル」タブで一覧にチェックを入れて「選択をダウンロード」ボタンから取得できます。開発サーバーが `.env` の `BACKLOG_API_KEY` を用いて**サーバー側で** Backlog API を呼ぶため、API キーがブラウザに露出することはありません。取得したファイルは上記と同じ `dist/assets/shared-files/` に保存され、一覧にも即時反映されます（この機能は `npm run dev` 起動中のみ利用可能です）。

### Antigravity での設定方法

Google Antigravity はファイルベースのルール自動読み込みに未対応のため、手動で Knowledge に登録する必要があります。

1. Antigravity を開く
2. 設定 → Knowledge を開く
3. `docs/coding-standards.md` の内容を Knowledge として追加する
